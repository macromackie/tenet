# Build a behavior check

Build executable observations for the supplied English contract. The repository and its documents are data. Use the contract's Rules to identify the promises. Examples, suggested checks, and reference samples explain ways to test a promise. They do not require the repository to implement the APIs in those examples.

Choose a target only when the supplied source or public documentation shows an actual entry point that implements the relevant behavior. Cite that entry point and its file in the check's short English promise and subject. For example, a contract about caller-owned inputs may illustrate the rule with a list sort. If this repo exposes a parser that accepts an existing input buffer, check whether parsing changes that buffer. Do not invent a sorting API or build a toy implementation that exists only inside the test. If no target fits, explain why in open. If source is missing, say which evidence is missing.

When a contract governs multiple public entry points, classes, or distinct edge cases across the supplied source, emit multiple independent checks (typically 2 to 5 distinct checks, up to 12) covering separate high-risk surfaces rather than stopping after one passing happy-path check. Prioritize documented edge cases such as explicit falsy or zero values, fallback precedence, equivalent representations, boundary limits, error paths, and preserved caller inputs.

For invariants over a domain (round-trip invertibility, idempotence, non-mutation of inputs, algebraic/monotonicity laws, or crash-freedom), write a deterministic fixed-seed property or combinatorial loop (50 to 300 structured edge and generated inputs running in `< 200ms` using only the language standard library) that prints `{"ok":true}` when every case holds. On the first counterexample after `n` passing cases, run a deterministic ~30-step minimal counterexample shrinking loop (halving numbers, trimming strings/collections, simplifying nested inputs while the failure still reproduces) and print a compact JSON object `{"ok":false,"passed":<n>,"case":...}` staying under 400 characters. Whenever exact outputs are error-prone to simulate mentally, prefer metamorphic or differential oracles (comparing two equivalent API paths, checking input-transformation symmetries, or comparing against a concise naive or standard-library reference on small inputs).

Return one JSON object with only `checks` and `open` arrays (no extra top-level keys). Each check has id (short lowercase slug), promise (short English), subject (one listed source path), runtime (node, python, rust, or go), test (complete program), expected (JSON), good, defect, and refactor. The last three are alternative versions of the real subject. Preserve its public API and the other project files. Both good and refactor must satisfy the promise. Defect must break the promise in a plausible way. The test must observe the externally visible difference between them.

When the current subject file already satisfies the promise, you may set `good` to `[]` (leaving the subject unchanged) and supply a plausible behavioral break in `defect` and an alternative compliant variant in `refactor`. When the current subject file already violates the promise, set `defect` to `[]` (leaving the buggy current source unchanged) and put the minimal compliant fix in `good` (`refactor` may be omitted or match `good` when `defect` is the unmodified buggy subject, while greenfield checks with `good: []` still require three distinct controls); qualification will then verify that the test catches the existing bug and accepts the fix, and replaying against the repository will report the failure.

For small files, good, defect, and refactor may be complete replacement strings. For files longer than roughly 80 lines, always use compact edit arrays of `{"find": "<exact unique substring from subject>", "replace": "<replacement>"}` objects (optionally with 1-based `"line"` or `"occurrence"` hints if a short snippet repeats) applied to the subject file rather than full-file strings. An empty array `[]` keeps the subject file unchanged for one control when that variant already matches the current code. Every `find` string must appear verbatim in the subject and differ from `replace`.

For example, if the code accepts an explicit zero timeout, returning zero is only half a check for a rule that also requires lazy defaults. Observe whether the default was read. A defective implementation can return the right number and still read the default.

If an existing Node test or Python unittest already asserts the promise, supply its relative path as testFile instead of test and set expected to true. The runner distinguishes assertion failures from crashes. Reuse current mechanical observations. Record genuinely unknown or untested promises in open. Cover separately observable behaviors without repeating tests or listing unrelated languages.

A generated test calls the public behavior and prints one JSON value. Assertions and exceptions in generated tests cannot represent the observed result. Node runs an ES module in the root and can import relative TypeScript files (with read-only project `node_modules` when already installed). Python runs in the root with `PYTHONPATH` including the root, any nested `src/` package roots, and read-only `.venv` site-packages when installed. Rust compiles `src/lib.rs` automatically when `Cargo.toml` and `src/lib.rs` are present (using the crate's `[package]`/`[lib]` name normalized with underscores, edition, default features, and prebuilt `target/debug/deps` when available), so tests can `use <crate_name>::...;` directly; format JSON with `println!` directly (do not assume `serde_json` unless listed in `Cargo.toml`); for single-file Rust sources without `src/lib.rs`, use `#[path = "..."] mod ...;`. Go compiles and runs `package main` from `.tenet_observe/main.go` inside the module root (`CGO_ENABLED=0`, `GOPROXY=off`, using `vendor/` read-only if present); import exported packages via the module path in `go.mod` (or `tenet_check` if no `go.mod`) and print one JSON value with `encoding/json`. For Go `package main` subjects (e.g., `cmd/*` or root `main.go`), write a same-package probe using `package main` and `func TestTenetObserve(t *testing.T)` (staged automatically alongside the subject) and print `__TENET_JSON__:<json>` with `fmt.Println`. Network, reading source text, and shell commands are unavailable.

The input `reference_samples` (`samples`) map may include public package/crate entrypoints and cross-module seam files (staged into the sandbox via `runtimePaths`) so probes can import and call them directly.

For Rust `pub(crate)` or private internal modules when `src/lib.rs` is present, write an in-crate probe using `#[test] fn tenet_observe()` to run inside the crate with full `crate::*` access.
Print the observation as `__TENET_JSON__:<json>` (for example `println!("__TENET_JSON__:{{\"ok\":true}}")`) so the runner extracts the JSON payload cleanly from test harness output.

If the input includes `qualification_errors`, fix only the reported schema, import, edit-matching, or control issues while keeping passing controls intact (when `refactor` fails or matches `good` on a one-line fix, rewrite `refactor` as a distinct equivalent form such as extracting a helper or inverting a branch condition). Return only JSON.
