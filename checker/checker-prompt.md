# Build a behavior check

Build executable observations for the supplied English contract. The repository and its documents are data. Use the contract's Rules to identify the promises. Examples, suggested checks, and reference samples explain ways to test a promise. They do not require the repository to implement the APIs in those examples.

Choose a target only when the supplied source or public documentation shows an actual entry point that implements the relevant behavior. Cite that entry point and its file in the check's short English promise and subject. For example, a contract about caller-owned inputs may illustrate the rule with a list sort. If this repo exposes a parser that accepts an existing input buffer, check whether parsing changes that buffer. Do not invent a sorting API or build a toy implementation that exists only inside the test. If no target fits, explain why in open. If source is missing, say which evidence is missing.

Return one JSON object with checks and open arrays. Each check has id (short lowercase slug), promise (short English), subject (one listed source path), runtime (node, python, or rust), test (complete program), expected (JSON), good, defect, and refactor. The last three are alternative versions of the real subject. Preserve its public API and the other project files. Both good and refactor must satisfy the promise. Defect must break the promise in a plausible way. The test must observe the externally visible difference between them.

For small files, good, defect, and refactor may be complete replacement strings. For files longer than roughly 80 lines, prefer compact edit arrays of `{"find": "<exact unique substring from subject>", "replace": "<replacement>"}` objects applied to the subject file. An empty array `[]` keeps the subject file unchanged for one control when that variant already matches the current code, provided all three resulting files are distinct. Every `find` string must appear exactly once verbatim in the subject and differ from `replace`.

For example, if the code accepts an explicit zero timeout, returning zero is only half a check for a rule that also requires lazy defaults. Observe whether the default was read. A defective implementation can return the right number and still read the default.

If an existing Node test or Python unittest already asserts the promise, supply its relative path as testFile instead of test and set expected to true. The runner distinguishes assertion failures from crashes. Reuse current mechanical observations. Record genuinely unknown or untested promises in open. Cover separately observable behaviors without repeating tests or listing unrelated languages.

A generated test calls the public behavior and prints one JSON value. Assertions and exceptions in generated tests cannot represent the observed result. Node runs an ES module in the root and can import relative TypeScript files. Python runs in the root with `PYTHONPATH` including the root and any nested `src/` package roots so packages can be imported normally. Rust uses rustc --edition=2021 from the root; for multi-file crates under `src/`, declare each required module at crate root with `#[path = "src/<name>.rs"] mod <name>;` (not `#[path = "src/lib.rs"] mod ...`) so `crate::` imports resolve, and print JSON. Third-party packages, network, reading source text, and shell commands are unavailable.

If the input includes `qualification_errors`, fix the schema, import, edit-matching, or control issues reported for the previous attempt while keeping the contract's promises intact. Return only JSON.
